# CodeOffer 设计规格说明书

> 日期:2026-08-09
> 状态:已与用户确认(MVP 设计)

## 1. 背景与目标

**核心目标**:利用 AI 技术将 GitHub 上的开源项目转化为个人简历上的核心竞争力,实现从"代码阅读"到"Offer 获取"的高效转化。

**两个核心痛点**:
1. 学习转化难:开源项目多,但只停留在"跑通代码",缺乏深度理解和内化。
2. 简历产出难:做过很多 Demo,但不知道如何挖掘亮点,难以转化为 STAR 描述。

**产品形态定位**:个人本地工具,通过本地 Web 应用使用,无账号体系,数据本地存储。

## 2. 需求基线(澄清结论)

| 维度 | 决策 |
|---|---|
| 产品定位 | 个人本地工具,单用户,无账号体系 |
| 使用形态 | 本地 Web 应用(浏览器访问) |
| AI 提供商 | 国内大模型 API(DeepSeek / 通义 / 智谱,可配置切换) |
| 人机协作 | AI 生成草稿 → 用户审阅/编辑/补充 → 确认后入库 |
| MVP 范围 | 完整链路但浅做:仓库解析 → 知识卡片 → STAR 简历描述 + 面试题 |

## 3. 总体架构(方案 A:双层服务式)

```
┌────────────────────────────────────────────────┐
│  浏览器  React + Vite + Ant Design(SPA)       │
└──────────────────────┬─────────────────────────┘
                       │ HTTP (JSON)
┌──────────────────────▼─────────────────────────┐
│  Java 层 · Spring Boot 3(端口 8080)            │
│  ├─ 业务编排:项目 CRUD、任务状态机、草稿编辑   │
│  ├─ AI 调用客户端:调 Python 服务(HTTP)         │
│  ├─ 持久化:SQLite + Spring Data JPA            │
│  └─ 静态托管:打包后的前端产物                  │
└──────────────────────┬─────────────────────────┘
                       │ HTTP (JSON, 流式 SSE 可选)
┌──────────────────────▼─────────────────────────┐
│  Python 层 · FastAPI(端口 8000)                │
│  ├─ 仓库抓取:GitPython 克隆到本地缓存目录      │
│  ├─ 代码解析:目录树/语言统计/关键文件提取      │
│  ├─ 提示词编排:结构化 prompt(架构/难点/亮点)   │
│  ├─ LLM 网关:统一接口,适配 DeepSeek/通义/智谱  │
│  └─ 生成任务:知识卡片 / STAR 简历 / 面试题     │
└────────────────────────────────────────────────┘
```

**职责边界(硬性约定)**:
- Java 永远不直接碰模型 API;Python 永远不碰业务数据库。
- 两层之间只通过 HTTP 契约交互(JSON)。
- 各组件可独立测试、独立演进;未来可把 Python 服务换成任意 AI 网关。

**启动方式**:Docker Compose 或本地脚本一键拉起两层服务;前端构建产物由 Java 层静态托管。

## 4. 数据流与数据模型

**核心流程(项目状态机)**:

```
[录入仓库 URL] → [抓取中] → [解析中] → [生成草稿中] → [待确认] → [已入库]
                                                              │
                                    ┌─────────────────────────┘
                                    ▼
                         [已入库] → 可随时重新生成/编辑/导出
```

**数据模型(3 张核心表 + 1 张任务表)**:

| 表 | 关键字段 | 说明 |
|---|---|---|
| `project` | id, repo_url, name, description, tech_stack(JSON), status | 一个 GitHub 仓库为一个项目 |
| `knowledge_card` | id, project_id, type(架构/难点/亮点/学到的), content, ai_draft, edited_at | 知识卡片,保留 AI 草稿与定稿 |
| `resume_entry` | id, project_id, star_content(JSON: situation/task/action/result), interview_qas(JSON 列表) | 简历条目 + 面试问答库 |
| `gen_task` | id, project_id, type, status, progress, error_msg, timestamps | 异步生成任务,驱动进度条与失败重试 |

**人机协作落点**:`knowledge_card` 与 `resume_entry` 同时存 `ai_draft`(AI 原始草稿)与用户编辑后的定稿;界面提供"重新生成 / 采纳草稿 / 手动编辑"三种操作。用户编辑过的内容标记为"已修改",不被后续重新生成覆盖。

**本地存储**:全部数据在单个 SQLite 文件 `data/codeoffer.db`;仓库克隆缓存于 `data/repos/<project_id>/`,可一键清理。

## 5. MVP 功能清单

1. **项目录入**:粘贴 GitHub 仓库 URL → 一键发起处理。
2. **仓库解析**:Python 服务克隆仓库(`--depth 1`)→ 输出目录树、语言/框架统计、核心文件清单。
3. **知识卡片生成**:AI 生成 4 类卡片(架构设计 / 技术难点 / 项目亮点 / 学习收获),每张卡片有 AI 草稿 + 可编辑。
4. **简历产出**:AI 生成符合 STAR 法则的项目描述(situation/task/action/result),可编辑。
5. **面试题库**:AI 生成 5-10 道针对该项目的模拟面试题(含参考答案),分基础/进阶/深挖。
6. **成果管理**:项目列表页、卡片/简历浏览页、导出(Markdown;简历可复制到求职平台)。

## 6. 人机协作关键交互

- 处理过程异步化:前端显示进度条(抓取→解析→生成各阶段),不阻塞页面。
- 每份 AI 产物旁有"重新生成(换角度)"按钮,便于反复打磨。
- 编辑后的内容带"已修改"标记,不被重新生成覆盖。
- 面试题支持"追问模式"(P1 扩展):选一道题让 AI 扮演面试官深挖。

## 7. 错误处理

| 场景 | 处理 |
|---|---|
| 仓库不存在/私有/网络失败 | 状态机置 failed,错误入库,前端可重试 |
| 大仓库(>100MB) | `--depth 1` 浅克隆,超限给出提示 |
| LLM API 超时/限流/余额不足 | LLM 网关统一重试(指数退避),友好错误提示 |
| API key 未配置 | 首次启动引导页填写,key 存本地配置文件 |
| 生成内容格式异常 | 网关层 JSON 校验 + 修复重试,失败降级为纯文本 |

## 8. 测试策略

- **Python 侧**:pytest 单测覆盖解析器与 LLM 网关(mock 模型响应,不产生真实 API 费用)。
- **Java 侧**:Spring Boot Test 覆盖业务编排与状态机(H2 内存库)。
- **端到端**:`scripts/e2e.sh` 拉起两层服务,用真实小型仓库跑通全链路。

## 9. 成功标准(MVP 验收)

- 输入任意一个中小型公开 GitHub 仓库,可完整走通:录入 → 解析 → 知识卡片 → STAR 简历描述 → 面试题。
- 用户可对每份 AI 产物进行编辑并持久化,重新生成不覆盖已编辑内容。
- 两层服务一条命令启动,数据与缓存均在本地目录,可整体清理。
- 简历产物可直接复制用于真实求职平台。

## 10. 扩展路线图(非 MVP,仅记录方向)

**P1(下一迭代)**
- 追问面试模式:AI 扮演面试官基于知识卡片连续深挖。
- 导出增强:简历一键导出 PDF,对齐主流招聘平台格式。
- 多仓库对比:相似项目并排对比,提炼差异化亮点。

**P2(中期)**
- 学习打卡与遗忘曲线:卡片复习提醒,基于间隔重复算法。
- 周报/总结生成:一周学习的项目自动汇总成求职周报。
- 简历库管理:多份简历、按岗位定制 STAR 侧重。

**P3(远期/个人品牌)**
- 技术博客一键生成:知识卡片转 Markdown 博客文章。
- AI 面试陪练:语音问答 + 实时反馈。
- 多用户化:账号体系、数据隔离(数据模型预留 owner 扩展余地)。
